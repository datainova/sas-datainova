Backend — Documentação Detalhada (DataInova SaaS)
Especificação técnica do backend para o SaaS de Objetivos Estratégicos, KResults e KPIs, incluindo ingestão via Data Innova Agent, conectores RO (Free/Pro), MCP e integrações (Stripe/HubSpot/Slack/Teams). Linguagem: Node.js + TypeScript.

0) Princípios
	•	NãoBI: armazenamos apenas agregados por período (sem dados linhaalinha do cliente).
	•	Multitenant por RLS: todas as leituras/escritas restritas a org_id.
	•	Contratos primeiro: OpenAPI + Zod; ferramentas MCP espelham as operações REST.
	•	Idempotência e versionamento: ingestão, webhooks e jobs resilientes.
	•	Observabilidade by design: logs estruturados, métricas e traces em 100% das rotas e jobs.

1) Visão de Arquitetura do Backend
Componentes:
	•	API (Fastify/TS): módulos por domínio (organizations, objectives, indicators, segments, values, agents, ingest, alerts, checkins, billing, leads, integrations, mcp).
	•	Workers (pgboss): ingestão, coleta RO, webhooks (Stripe/HubSpot), alertas, backfills.
	•	PostgreSQL: relacional, RLS por org_id, partições para séries de valores, índices dedicados.
	•	Chroma: vetorial para busca semântica (glossário/sugestões de nomes/segmentações).
	•	MCP Server: transporte HTTP streamable (prod) e stdio (dev) expondo Tools/Resources/Prompts.
Padrões:
	•	DDD leve por módulos; services puros tipados.
	•	Plugins Fastify para auth, db, ratelimit, pino logger, otel.
	•	Prisma como ORM; migrações versionadas.

4) Autenticação, Autorização e Multitenancy
4.1 Auth
	•	JWT assinado pelo backend (ou provedor SSO no Enterprise) contendo sub, org_id, roles[], plan.
	•	Refresh tokens curtos; rotação a cada login.
4.2 RBAC
	•	Perfis: ORG_OWNER, MANAGER, CONTRIBUTOR, VIEWER.
	•	Escopos adicionais para MCP (tool:*, resource:*).
4.3 Multitenant com RLS
Abordagem: 1 banco, 1 esquema, todas as tabelas com coluna org_id + RLS.
Sessão: em cada request, após validar o token, o backend executa:
-- por transação
SELECT set_config('app.current_org_id', $orgId, true);
SELECT set_config('app.current_roles', $rolesCsv, true);
Política (exemplo):
-- Habilitar RLS
ALTER TABLE objective ENABLE ROW LEVEL SECURITY;

-- Política padrão
CREATE POLICY objective_isolate_org ON objective
USING (org_id = current_setting('app.current_org_id')::uuid)
WITH CHECK (org_id = current_setting('app.current_org_id')::uuid);
Nota: As queries do Prisma devem rodar dentro de uma transação que inicia com o SET LOCAL acima; um helper withOrgContext(orgId, fn) encapsula a execução.

6) Políticas de RLS (SQL)
-- Exemplo genérico para tabelas com org_id
CREATE POLICY org_select ON indicatorvalue
  FOR SELECT USING (org_id = current_setting('app.current_org_id')::uuid);
CREATE POLICY org_insert ON indicatorvalue
  FOR INSERT WITH CHECK (org_id = current_setting('app.current_org_id')::uuid);
CREATE POLICY org_update ON indicatorvalue
  FOR UPDATE USING (org_id = current_setting('app.current_org_id')::uuid)
              WITH CHECK (org_id = current_setting('app.current_org_id')::uuid);
Boas práticas:
	•	ALTER TABLE ... ENABLE ROW LEVEL SECURITY;
	•	ALTER TABLE ... FORCE ROW LEVEL SECURITY; (impede bypass por superuser não esperado).
	•	Toda INSERT deve preencher org_id pela camada de serviço (derivado do token do usuário/agent).

8) Ingestão — Data Innova Agent (Enterprise)
8.1 Handshake e Registro
	•	Registro: POST /agents/register (OrgOwner/DataAdmin) emite agentId + apiKey (curta duração para primeiro boot).
	•	O Agent troca por chave de assinatura de longa duração (AGENT_SIGNING_SECRET escopo org/agent) e armazena no seu cofre local.
8.2 Assinatura de Payload (HMACSHA256)
X-Agent-Id: <agentId>
X-Signature: sha256=<hex(hmac(body, agent_secret))>
X-Batch-Id: <uuid>
8.3 Contrato de Ingestão
POST /ingest/indicator-values
{
  "indicatorId": "uuid",
  "periodStart": "2025-09-01",
  "granularity": "MONTHLY",
  "segmentKey": {"Estado":"SP","Canal":"Direto"},
  "value": 123456.78,
  "checksum": "abc123",
  "sourceMeta": {"job":"receita_liquida_mensal","rowsRead": 53211}
}
Respostas: 202 Accepted (processamento assíncrono) ou 409 Conflict (batch duplicado), 401 (assinatura inválida).
8.4 Idempotência & Processamento
	•	Dedupe por X-Batch-Id no DataTransferBatch. Se já processado, retornamos 409.
	•	Worker ingest-batch-processor valida schema, HMAC, checksum, aplica RLS por org_id do agente e upserta IndicatorValue com version apropriada.
8.5 Reprocessamento / Versões
	•	Reenvio do mesmo periodStart e segmentKey com version = last+1 (histórico preservado). A visualização padrão usa a maior versão.

9) Conectores RO (Free/Pro)
	•	Conectores para BigQuery, Snowflake, Redshift, Databricks, Postgres/SQL Server.
	•	Execução serverside de queries apenas agregadas; validações antiexpansão (LIMIT, HAVING/ROLLUP verificadas por linter simples, allowlist de funções).
	•	Credenciais guardadas em cofre e referenciadas por Connector (somente metadados ficam no Postgres).
	•	Jobs connector-pull executam de acordo com a cadência do indicador; staleness gera alerta.

10) Cálculo de Status
export function statusFrom(target: number, tol: number, dir: Direction, val: number){
  if(dir==='INCREASE') return val >= target ? 'ON' : (val >= target*(1 - (tol||0)) ? 'RISK' : 'OFF')
  if(dir==='DECREASE') return val <= target ? 'ON' : (val <= target*(1 + (tol||0)) ? 'RISK' : 'OFF')
  return Math.abs(val - target) <= (tol||0) ? 'ON' : 'OFF'
}
	•	Aplicase por período (na ingestão) e reprocessamentos atualizam statusCalc.

11) Alertas & Checkins
	•	Alertas: staleness (sem valor novo após cadence SLA), desvio (OFF/RISK), falhas de ingestão. Destinos: Slack/Teams/email.
	•	Checkins: POST /checkins com objectiveId|indicatorId, período, status e notas.
	•	Jobs staleness-checker e alert-dispatcher rodam em pgboss.

12) Billing (Stripe) & Planos
	•	Free: limites rígidos (nº objetivos, KRs/KPIs) e/ou cadência mínima.
	•	Pro: ilimitado no SaaS; sem Agent.
	•	Enterprise: habilita Agent.
Webhooks Stripe (/webhooks/stripe): checkout.session.completed, customer.subscription.updated|deleted, invoice.payment_succeeded|failed.
	•	Idempotência por event.id (tabela WebhookEvent opcional) e aplicação de Entitlements.

13) Leads (HubSpot)
	•	Upsert de Company após finalização do onboarding (nome, país, segmento, porte, missão, visão).
	•	Associação ao lead/contact quando existir; erros vão para DLQ (webhook-dispatcher).

14) Observabilidade
14.1 Logging (Pino)
	•	JSON estruturado com ts, requestId, orgId, actor, route, status.
	•	Redação de campos sensíveis; limites de tamanho.
14.2 Métricas
	•	Otel Metrics: latência por rota, taxa de erro, throughput de ingestão, jobs em andamento, staleness média, utilização de quotas.
14.3 Tracing
	•	Otel Traces com traceId propagado entre API ↔ Workers; spans para DB/HTTP (Stripe/HubSpot/Slack).

15) Rate Limiting & Quotas
	•	Rate limit por usuário e tenant (token bucket em plugin; armazenamento em memória por nó + leaky bucket por IP; em HA, considerar store Postgres simples para endpoints críticos).
	•	Quotas (por plano): nº de objetivos, KRs/KPIs, frequência mínima de sync, nº de alertas/dia.

16) Segurança
	•	TLS 1.2+, headers de segurança (CORS, HSTS, CSP mínima para API).
	•	RLS forçada; privilégios mínimos para usuários DB; migrações feitas por role separada.
	•	Assinaturas de webhooks (Stripe/HubSpot) e Agent verificadas e auditadas.
	•	PII não persistida nos valores; logs sem payloads sensíveis.
	•	Secrets rotacionados; chave do Agent por tenant/agent.

17) Testes
	•	Unit: serviços puros (status calc, normalização de segmentação).
	•	Integration: módulos Fastify com Postgres de teste (containers) e prisma migrate.
	•	Contract: validação OpenAPI/Zod (schemathesis/prism opcional).
	•	E2E: rotas chave (onboarding, objetivo, KR, ingestão, webhook Stripe) com dados sintéticos.

18) CI/CD
	•	CI: lint (ESLint), typecheck (tsc), testes unit+integration, cobertura.
	•	Build: docker multistage; varredura de vulnerabilidades.
	•	CD: prisma migrate deploy → deploy app → smoke tests; feature flags para toggles.
	•	Rollback: imagens versionadas e migrações backwardcompat quando possível.

19) Runbooks SRE
	•	Ingestão parada: checar fila pgboss, DLQ e conectividade; reprocessar lotes.
	•	RLS bloqueando: verificar app.current_org_id setado na transação; logs de auth.
	•	Staleness alto: revisar cadências/config de conectores; health do Agent.
	•	Stripe falhando: fila de eventos pendentes; reentrega com backoff.

20) Padrões de Código (Node/TS)
	•	strict: true, noImplicitAny, esModuleInterop: false.
	•	Fastify + @fastify/ajv-compiler para validação de payloads (ou Zod adapter).
	•	Pino para logs; fp-ts opcional para flows funcionais simples.

21) MCP — Backend
	•	Tools mapeiam serviços REST (ex.: objective.create, kr.create, indicator.values.list, agent.batch.ingest).
	•	Resources somenteleitura (URIs lógicas: objective://{id} etc.).
	•	Prompts (ex.: draft-objective-from-mission).
	•	Segurança: mesmo RBAC/entitlements do REST; ratelimit por tool; logs McpToolInvocationLog.
21.1 Exemplo de Tool
registerTool({
  name: 'kr.create',
  inputSchema: zodToJsonSchema(CreateIndicator),
  handler: async (input, ctx) => {
    const orgId = ctx.auth.orgId
    return withOrgContext(orgId, () => indicatorsService.createKR(input))
  }

22) Normalização de Segmentação
	•	Entrada livre no wizard → Axis/Value persistidos com code (slug) calculado.
	•	segmentKey no valor é JSON ordenado com chaves alfabetizadas; índice GIN para consultas por filtro.

23) Desempenho & Escala
	•	Particionamento de IndicatorValue por mês.
	•	Índices: (org_id, indicator_id, period_start); GIN para segment_key.
	•	Batching na ingestão (lotes até 1–5k linhas); compressão gzip.
	•	Backpressure: fila pgboss por org_id.

24) Retenção & Compliance
	•	IndicatorValue: retenção indefinida (agregados), configurável por tenant.
	•	AuditLog: 24 meses (padrão) — exportável antes da expiração.
	•	Webhooks/raw: 30 dias em DLQ.

25) Matriz de Permissões (resumo)
	•	ORG_OWNER: tudo na org.
	•	MANAGER: CRUD objetivos/indicadores; ver valores e alertas.
	•	CONTRIBUTOR: atualizar checkins; ver indicadores.
	•	VIEWER: leitura.
	•	DATA_ADMIN (Enterprise): gerenciar Agent e conectores.
