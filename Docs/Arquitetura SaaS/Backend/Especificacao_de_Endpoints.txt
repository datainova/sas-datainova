
Especificação de Endpoints — DataInova Connect (SaaS v1)
Objetivo: descrever os endpoints REST (v1) do SaaS para implementação pelo backend, com contratos de requisição/resposta, validações, segurança, idempotência e telemetria. Abrange autenticação, onboarding, organização/membros, objetivos/indicadores/metas/valores, ingestão (Agente → SaaS), check-ins, alertas, agentes, webhooks e observabilidade.
1) Convenções Gerais
Base URL: /v1 (ex.: https://api.datainova.com/v1).
Formato: application/json; charset=utf-8.
Autenticação: Bearer (JWT/OIDC) em Authorization: Bearer &lt;token&gt; ou sessão (cookies httpOnly/SameSite estritos).
Correlação: exigir/propagar x-request-id (UUID) e traceparent (W3C). Responder sempre com os dois.
Erros: RFC 7807 (application/problem+json). Campos: type, title, status, detail, instance, code, correlation{request_
id,trace
_id} e (quando útil) context.
Paginação: cursor-based. Query
: ?limit
=50&amp;cursor=&lt;opaque&gt;. Resposta inclui
{ "
page": { "next": "...", "size": 50 } }.
Cache e freshness: updatedSince=ISO8601 em lists; ETag/If-None-Match nos GETs idempotentes.
Multitenancy/RLS: o tenant é inferido do token; não aceitar organization_id no corpo. Toda transação executa com SET LOCAL
app.organization
_id.
Enum de período: granularity ∈ {
DAY,WEEK
,MONTH,QUARTER,YEAR}. period_start sempre início do período no fuso da org, convertido a UTC.
Segmentação: segment_key é JSON canônico (chaves ordenadas, valores determinísticos); segment_hash = sha256(serialize(segment_key)).
Idempotência: ver seções específicas (ingestão e webhooks).

4.6 Ingestão (Agente → SaaS)
POST /ingest/indicator-values
Headers obrigatórios:X-Agent-Id: uuidX-Batch-Id: string (idempotência)X-Signature: sha256=&lt;hmac(body, agent_secret)&gt;
Body:
{
  "items": [
    {
      "indicator_id": "uuid",
      "period_start": "2025-10-01T00:00:00Z",
      "granularity": "MONTH",
      "segment_key": {"country":"BR"},
      "value": 100.5
    }
  ]
}
202 { accepted: n, duplicate: d, conflict: c }
409 (Problem+JSON) quando conflito de estado; 401 assinatura inválida; 429/5xx com retry-after.
Regras: somente agregados; deduplicação por (organization_id, batch_id, checksum); merge com advisory locks por (
indicator,period
,segment_hash).

4.13 Observabilidade e MCP
GET /health (sem tocar DB).GET /ready (migrations, conexões, workers ok).GET /metrics (Prometheus).
POST /mcp — transporte JSON-RPC 2.0 do MCP (tools/resources/prompts). Suporta batch; rate limit conforme plano (free=60 rpm, pro=120 rpm, enterprise=300 rpm).
POST /mcp/stream — execução MCP via Server-Sent Events (somente planos pro/enterprise).
GET /mcp/capabilities — catálogo dinâmico de tools/resources/prompts e limites habilitados para o tenant. Retorna plano corrente, transports habilitados ({ http, sse, websocket }) e quotas rpm.
Notas: requere autenticação igual às rotas REST; roles e planos controlam acesso (ex.: agents.* apenas admin+enterprise, nai.* apenas editor+pro/enterprise).
5) Validações &amp; Regras por Domínio
Período: period_start deve alinhar ao início do período conforme granularity e TZ da org; rejeitar fora de alinhamento.
Segmento: aceitar apenas chaves/valores previstos pela segment schema do indicador (quando definida); normalizar e computar segment_hash.
Indicadores/Metas: direction ∈ {
UP,DOWN
,RANGE}; tolerance 0..1 (percentual); metas podem sobrescrever tolerância.
Ingestão: cada lote gera ingest_batch + ingest_item{n}; bloquear reprocesso com mesmo (batch_id, checksum); CONFLICT quando o mesmo lote traz valor divergente do último merge para (indicador, período, segmento).
RLS: todos os handlers devem definir
app.organization
_id no início da transação; recusar qualquer organization_id vindo do cliente.

7) Segurança &amp; Ratelimit
Auth: Argon2id (senhas), OIDC (Google), Magic Link; cookies httpOnly/SameSite; CORS restrito.
Headers sensíveis: nunca logar authorization, cookie ou x-signature do Agente; redigir por default.
Ratelimit padrão:POST /auth/login 10/min por IP; POST /ingest/indicator-values 300/min por agente (ajustável por plano).
TLS: obrigatório; rejeitar downgrade.
8) Exemplos rápidos (cURL)
Ingestão
curl -X POST "$API/v1/ingest/indicator-values" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Agent-Id: $AGENT_ID" \
  -H "X-Batch-Id: b-2025-10-01" \
  -H "X-Signature: sha256=$SIG" \
  -d '{"items":[{"indicator_id":"'$IND'","period_start":"2025-10-01T00:00:00Z","granularity":"MONTH","segment_key":{"country":"BR"},"value":100.5}]}'
Consulta de valores
curl "$API/v1/indicators/$IND/values?range=2025-01-01..2025-10-01&amp;latestOnly=true&amp;segment={\"country\":\"BR\"}"

10) Critérios de Aceite (gerais)
RLS aplicado a todas as rotas de dados; nenhuma leitura crosstenant em testes.
Ingestão idempotente; reentregas não criam duplicatas; conflitos sinalizados via 409.
Views e consultas entregam latest quando solicitado; filtros por período/segmento operam em índices.
Logs estruturados com request_id, tenant_id, trace_id; sem segredos.
SLO de leitura (p99 ≤ 400ms em chamadas de consulta comum com filtros).
